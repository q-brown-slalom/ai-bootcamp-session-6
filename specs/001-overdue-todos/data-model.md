# Data Model: Overdue Todo Items

**Feature**: 001-overdue-todos  
**Date**: 2025-12-16  
**Status**: Phase 1 Design

## Overview

This feature adds overdue detection capabilities to the existing Todo entity. No database schema changes are required - overdue status is **derived state** calculated on the frontend from existing fields.

## Entities

### Todo (Existing Entity - No Changes Required)

The Todo entity already contains all necessary fields for overdue detection. No schema modifications needed.

**Fields**:
- `id` (string, required, unique): Unique identifier for the todo
- `title` (string, required, max 255 characters): Todo description
- `dueDate` (date, optional, ISO 8601 format): When the todo should be completed
- `completed` (boolean, required, default: false): Completion status
- `createdAt` (date, required, ISO 8601 format): Creation timestamp

**Storage**: SQLite database via better-sqlite3

**Validation Rules** (existing):
- `title`: Non-empty string, maximum 255 characters
- `dueDate`: Valid ISO 8601 date string or null
- `completed`: Boolean value
- `id`: Generated by backend (UUID)
- `createdAt`: Generated by backend (ISO timestamp)

**Example**:
```json
{
  "id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "title": "Finish project documentation",
  "dueDate": "2025-12-10",
  "completed": false,
  "createdAt": "2025-12-01T10:30:00.000Z"
}
```

## Derived State (Calculated, Not Stored)

### Overdue Status

**Definition**: A todo is considered overdue when:
- `completed` is `false` AND
- `dueDate` exists (not null) AND
- `dueDate` < current date (date-only comparison, excluding time)

**Calculation Location**: Frontend (client-side)

**Function Signature**:
```javascript
/**
 * Determines if a todo is overdue
 * @param {string|null} dueDate - ISO date string or null
 * @param {boolean} completed - Whether todo is completed
 * @returns {boolean} - True if overdue, false otherwise
 */
function isOverdue(dueDate, completed) {
  if (completed || !dueDate) return false;
  
  const today = new Date();
  today.setHours(0, 0, 0, 0);
  
  const due = new Date(dueDate);
  due.setHours(0, 0, 0, 0);
  
  return due < today;
}
```

**Truth Table**:

| completed | dueDate    | Current Date | isOverdue |
|-----------|------------|--------------|-----------|
| false     | 2025-12-10 | 2025-12-16   | true      |
| false     | 2025-12-16 | 2025-12-16   | false     |
| false     | 2025-12-20 | 2025-12-16   | false     |
| false     | null       | 2025-12-16   | false     |
| true      | 2025-12-10 | 2025-12-16   | false     |
| true      | null       | 2025-12-16   | false     |

**Performance**: O(1) per todo - simple date comparison

## UI State Models

### Filter Mode

**Type**: Local component state (not persisted)

**Values**:
- `"all"` (default): Display all todos
- `"overdue"`: Display only overdue todos

**State Location**: TodoList component (or parent container)

**Example**:
```javascript
const [filterMode, setFilterMode] = useState('all');
```

### Overdue Count

**Type**: Derived value (computed from todos array)

**Calculation**:
```javascript
const overdueCount = todos.filter(todo => 
  isOverdue(todo.dueDate, todo.completed)
).length;
```

**Display Location**: Application header next to "My Todos" title

**Format**: 
- When count > 0: "My Todos (3 overdue)"
- When count = 0: "My Todos"

## State Transitions

### Todo Lifecycle with Overdue Status

```
┌─────────────┐
│   Created   │
│ (no due    │
│  date)      │
└──────┬──────┘
       │
       │ Add due date
       │ (future)
       ▼
┌─────────────┐
│   Active    │
│  (future    │
│  due date)  │
└──────┬──────┘
       │
       │ Time passes
       │ (due date < today)
       ▼
┌─────────────┐
│  Overdue    │◄──────┐
│ (incomplete │       │
│  + past)    │       │ Edit date back
└──────┬──────┘       │ to past
       │              │
       │ Mark         │
       │ complete     │
       ▼              │
┌─────────────┐       │
│  Completed  │       │
│ (never      │       │
│  overdue)   │       │
└──────┬──────┘       │
       │              │
       │ Unmark       │
       │ complete     │
       ▼              │
       └──────────────┘
```

**State Rules**:
1. Completed todos can never be overdue (even with past due dates)
2. Todos without due dates can never be overdue
3. Overdue status updates immediately when:
   - Todo is marked complete/incomplete
   - Due date is edited
   - On component re-render (for midnight transitions)

## Validation Rules

### Date Validation (Existing Backend)

- Due dates must be valid ISO 8601 date strings
- Format: "YYYY-MM-DD" (date only, no time component)
- Backend validates format on create/update

### Frontend Validation (New)

- Date comparison logic validates that dates are parseable by JavaScript Date constructor
- Handle null/undefined due dates gracefully (treat as not overdue)
- No future validation needed - users can set any due date

## Data Integrity

**No Risk of Stale State**:
- Overdue status is calculated on every render from source data
- No cached overdue flags that could become stale
- Automatic updates when todos change

**No Database Constraints Needed**:
- Overdue is derived, not stored
- Existing todo constraints are sufficient

## Migration Requirements

**None required** - this feature uses existing data structures and adds no new persisted fields.
